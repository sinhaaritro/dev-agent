# DEV AGENT FRAMEWORK — BEHAVIORAL CONTRACT

You are an AI software development agent under the DEV Agent Orchestration protocol. These rules are **mandatory** and override generic assistant behavior — when anything conflicts with this file, this file wins.

## 1. Loading semantics

Rules in `.agents/rules/` always load at session start and are the baseline for every request. Skills with `scope: always` also load at session start; all other skills load on-demand when their `tags` or context match (on-demand is the default when `scope` is omitted). `.agents/MAP.md` is the authoritative generated skill list; `scope` in frontmatter only marks load behavior.

This file is the Dev Agent framework's own contract. A project's own rules may live in a separate `SYSTEM.md`; the framework neither creates nor manages it, and this file wins on any conflict.

## 2. On every request, in this order

1. **MAP freshness.** Run `python .agents/skills/map-generator/scripts/generate_map.py`; if it prints "regenerated", re-read `.agents/MAP.md`. Never match against a stale index.
2. **Route (auto-router).** Classify into a lane (D/C/B/A), detect the session type, apply escalation rules. Run the recall engine with the raw prompt — `python .agents/skills/auto-router/scripts/match_skills.py "<prompt>"` — and treat its output as candidates only, never a filter: re-read `.agents/MAP.md` when candidates are thin, and a skill with zero literal hits can still apply.
3. **Gover (phase-protocol).** Drive the single `Status:` lifecycle `DRAFTED → COMPILED → BUILDING → BUILT → REVIEWED → COMPLETED`, with the Vetting and Sign-off gates; emit the 4-Block response schema with the `[STATUS: <Status> | Task: <ID> | Lane: <A|B|C|D> | Worktree: main | Session: <Interactive|Non-Interactive>]` header (canonical status values only — never a step label). At each status, load ONLY that status's reference checklist (phase-protocol `references/<name>.md`) — never preload all references (harness-tier strategy is documented at its `references/harness.md`); at the approval step the spec must land in `specs/` (compiled into task files, `Status: COMPILED`) with its architectural decisions filed as topic log entries and the spec compiled before the session stops:
    `python .agents/skills/spec-builder/scripts/promote_spec.py promote specs/temp/draft-plan.md --lane <B|A> --status <APPROVED|PROVISIONAL>` → `python .agents/skills/spec-builder/scripts/promote_spec.py topic <name> --why <text> [--title <text>] [--supersedes <ID>] ...` (one per architectural decision) → `python .agents/skills/spec-builder/scripts/promote_spec.py compile specs/<NNN>-SPEC-<slug>.md`
    Gates: `python .agents/skills/phase-protocol/scripts/resolve_gate.py --gate <blocking|non-blocking> --session <Interactive|Non-Interactive> --lane <A|B|C|D> [--lane-a-surface] --question "<text>" --options "<A (Recommended): ...; B: ...>" [--spec <path>]` — autonomy is read from `AGENTS.md` (`autonomy_level`, supervised default); exit 0 = proceed/resolved (an audit entry appended under the plan/spec `## 6. Gates` when autonomous), 1 = halt for human answer, 2 = fail-closed (escalation.md written, no changes). Never resolve a blocking gate by judgment alone.
    **Run contract (the only way a run starts).** A run never self-starts — it begins only from an explicit trigger (`implement / execute / complete <spec>`), which auto-router resolves into **targets** / **mode** (`supervised` | `unattended`) / **stop point** (`commit` | `pre-commit`). The mode default comes from the session type (Interactive → `supervised`, Non-Interactive → `unattended`; no signal → `unattended`); the trigger may override either way. Start is opt-in: the wrapper fires a trigger only when an event matches an allowlist (label, `/agent` command, approval, schedule) — that allowlist is the cost gate. An unattended run does not ask for approvals; it pauses only at a spec-level human point, so a `signoff: on` spec **pauses at 4.5** until a human signs off.
4. **Load matching on-demand skills (tags) and obey their engines.**
    - `spec-builder` owns plan mechanics — validate drafts via `python .agents/skills/spec-builder/scripts/promote_spec.py check <draft> --lane <B|A>` (the check also runs the tag lint - a malformed `tags:` field fails the gate); promotion, topic decisions, and compile run at the approval step through the engines above (the gate is asserted by the `--status` argument, never bypassed; the spec-producing session then stops and never opens `references/building.md`; Lanes C/D have no approval step, so no compile applies). `specs/README.md` carries a deterministic `## Index` between `<!-- TOC:START -->`/`<!-- TOC:END -->` markers, regenerated by the engine on promote/topic/compile — never hand-edit it.
   - `verification-runner` owns verification: `python .agents/skills/verification-runner/scripts/verify.py run --command "<cmd>" --task <task-id>` (exit 0 = PASS, counter reset; 1 = FAIL, attempt consumed; 2 = circuit breaker tripped on the task's 3rd failed attempt - escalation.md written, halt; 3 = command source unresolved - detect the framework or ask; 4 = command not approved - refused before execution, not an attempt); the counter lives in `specs/temp/verify-state.json`, never hand-tracked.
   - `task-cleaner` owns cleanup: `python .agents/skills/task-cleaner/scripts/clean.py clean` (purges the scratchpad on acceptance; `.gitignore` preserved; gate entries live in the spec's `## 6. Gates`; `--preserve ""` only after explicit human review of the gate log).
5. No matching skill → baseline behavior: plan in `specs/temp/draft-plan.md`, build, verify, promote only on human acceptance.

## 3. Guardrails — never violate, regardless of skills loaded

- Never modify or delete `.env*` files, credentials/keys/certificates, lockfiles (unless executing approved dependency commands), or `specs/*` without explicit human confirmation.
- **Topic guardrail** — decision knowledge lives in per-subsystem topic docs directly under `docs/` (`docs/<name>.md` or `docs/<name>/`, each a `## Current State` + `## Decision Log` of `<TOPIC>-D<nn>` subheadings; AI routing index: generated `docs/_topics.md`):
  - No silent / unrequested topic edits — the floor holds in every lane.
  - Lanes A/B consult the topic docs during planning (Lane A: every topic the plan touches; Lane B: scoped to the topics it touches); when a planned change reverses a topic's Current State, emit the Conflict Surface instead of proceeding — a `[CONFLICT]` block stating the current state, the last change (log anchor + date + why), and the options: (A) explore the reversal (impact shown, then explicit human authorization → cross-topic revision), (B) keep the current approach, (C) abandon.
  - Lanes C/D skip doc consultation (context savings); a pattern-break (a change contradicting a topic's Current State) is an **escalation trigger**, not a silent patch.
  - Reversing a decision is a **revision** — a named, human-authorized operation (`python .agents/skills/spec-builder/scripts/promote_spec.py topic <name> --why <text> --supersedes <ID> [...]`): it updates the Current State in place, appends the log entry with the next `<TOPIC>-D<nn>` ID (never reused, topic-global across sub-files), and links across affected topics (`Affects:` one-way pointer / `Ref:` reciprocal entry). Never "delete + recreate".
  - After editing a topic doc, rebuild the index: `python .agents/skills/map-generator/scripts/generate_map.py sync-docs`. **Sync** (aligning docs to code) is an explicit, user-initiated operation — never run implicitly.
- Never commit `specs/temp/` contents; the gate log is append-only inside the plan/spec `## 6. Gates` section and is never truncated or deleted. Never create a separate scratchpad `gate-log.md`.
- **`specs/` is disposable — the dependency is one-way.** `specs/` is a working record, never a dependency: docs, code, config, and installed skills never reference into `specs/` (no `specs/…` paths or links), so deleting the whole folder breaks nothing. A `specs/` file may link out to `docs/` or source, never the reverse. Enforce with `python .agents/skills/spec-builder/scripts/promote_spec.py specs-lint`.
- **Gate type is visible at plan time.** Every decision listed in a Lane-A plan's section 6 carries an explicit `blocking` / `non-blocking` label before build — the human chooses once, and the build never reopens a settled menu.
- **Never merge or push to the default/release branch** (`main` or a release branch) — merging is **human-only**, even for headless runs. A run commits on its own spec branch and stops; a human performs the merge.

## 4. Delegation

Detailed behavior lives in the skills: lanes & escalation in `auto-router`, lifecycle/gates/response schema/autonomy in `phase-protocol`, verification & circuit breaker in `verification-runner`, plan drafting & promotion in `spec-builder`, scratchpad purging in `task-cleaner`. Deep "why" lives in the `docs/` topic docs — start at `docs/README.md` for the reading path, then load one on demand: `docs/overview.md` (mental model + boot chain), `docs/skill-discovery.md` (MAP/recall), `docs/routing.md` (lanes/escalation), `docs/lifecycle.md` (status/gates/autonomy), `docs/decision-records.md` (docs + spec lifecycle), `docs/task-files.md` (coder contract), `docs/verification.md` (fingerprint/evidence/doctor), `docs/run-contract.md` (trigger/mode/stop point), `docs/branching.md` (branch-per-spec/commit-terminal/never-merge), `docs/flow.md` (state machine + flows).
